# Telecart

A web administration workspace for a Telegram digital-product shop.

## Running this imported project on Replit

- Runtime: Node.js 24 (required for the existing native SQLite implementation); install dependencies with `pnpm install --frozen-lockfile`.
- Run the managed `artifacts/api-server: API Server` and `artifacts/telecart: web` workflows. The API serves `/api` on port 8080 and the dashboard serves `/` on port 18237 through Replit's shared preview proxy. The optional Canvas workflow is not required for the dashboard.
- Sign in with the configured `TELECART_ADMIN_EMAIL` and the password supplied securely as `TELECART_ADMIN_INITIAL_PASSWORD`. Keep `SESSION_SECRET` unchanged for encrypted data. No Clerk service or OTP is required for this explicitly owner-bound installation.
- Development `TELECART_ADMIN_ORIGIN` and `TELECART_PUBLIC_URL` must match the current workspace's HTTPS origin, not the source repository's old workspace URL. Update them through environment settings if the workspace domain changes.
- Keep `TELECART_TELEGRAM_DISABLED=true` for this preview. No external provider credentials were added or live sending/payment processing activated during import setup.
- SQLite initializes its existing schema automatically at startup at `data/telecart.db`; never commit the database or its locks/journals. Workspace data was not imported from a previous installation.
- Verification: `pnpm run typecheck`, `pnpm test:local`, `pnpm test:sqlite`, and `GET /api/healthz`. During import verification, typechecking and local tests passed; 42 of 43 SQLite regression files passed. The existing `shop-transfer.test.ts` table-list assertion expects 24 tables while the current schema has 26, including advertising checkpoints and membership jobs.
- Workspace preview only: do not use a published Replit app's ephemeral filesystem for live SQLite shop data. Use persistent-disk hosting for this existing storage design.

## SQLite storage — current source of truth

The user explicitly switched live storage from PostgreSQL to SQLite. Historical PostgreSQL-specific notes below describe the previous engine, not the current runtime. `TELECART_SQLITE_PATH` selects the file (default `data/telecart.db`, relative to the project root). All 24 tables now use SQLite builders and a native `node:sqlite` engine through Drizzle's async SQLite driver; no PostgreSQL server is used by the application. `pg` is retained only for the explicit read-only migration tool.

Write transactions hold a process-wide async mutex for their full lifetime and use `BEGIN IMMEDIATE`. An exclusive per-file process lock prevents two Telecart servers using the same shop; established session-level business locks remain held across network operations. Do not replace these with per-statement locks or no-op session locks. SQLite files and journals are excluded from Git and publish artifacts. Keep SESSION_SECRET and owner binding for existing encrypted data.

`scripts/migrate-postgres-to-sqlite.mjs --confirm-read-only-migration` copies an explicitly selected PostgreSQL source into an empty SQLite destination, validates counts/relationships/integrity, and pauses external processing. It never changes the source or runs during startup. Workspace data was converted with this tool.

Local setup now needs only Node 22.16+/24+ and pnpm. Use `start-local.bat` / `start-local.sh`, `pnpm test:local`, and `pnpm test:sqlite` (isolated synthetic SQLite fixtures). `pnpm --filter @workspace/db run push` initializes/checks the supported SQLite schema without destructive rewrites. See LOCAL_SETUP.md for existing-config conversion and portable ZIP instructions.

Portable ZIP format 2 remains compatible: `shop.db` plus README, plaintext portable stock/provider credentials after acknowledgement, destination re-encryption, empty-shop protection and processing holds. The portable schema fingerprint is intentionally engine-independent. Preserve ISO timestamp microseconds and JSON text rather than rounding large JSON numbers.

**Deployment limitation:** Replit's published-app filesystem is not durable across publishes/redeployments. This SQLite setup is intended for localhost/persistent-disk hosting and workspace preview, not live sales on a published Replit filesystem.

## Current scope

- Product creation, editing and deletion, encrypted credential inventory, nonsecret shop/bot/payment preferences and private owner workspaces.
- The dashboard requires admin sign-in on all routes. Unauthenticated read-only APIs serve safe samples or empty data, never private shop records.
- Dashboard sign-in is admin email and password only, with no Clerk widget or OTP. Existing shop ownership is preserved. The configured `TELECART_ADMIN_INITIAL_PASSWORD` secret now also supplies the admin login credential; changing it invalidates existing sessions. Sessions are random, stored as keyed hashes in PostgreSQL, expire after eight hours, and use Secure/HttpOnly/Partitioned cookies for the embedded preview. All writes require the configured exact Origin, and failed logins are rate-limited in the database.
- The phone mockup remains a **local preview**. The dashboard selects polling (including localhost) or public HTTPS webhooks after explicit admin activation.
- NOWPayments direct payments, address QR generation, HMAC-signed IPN verification plus authoritative API checks, integer wallet ledger and encrypted-stock delivery are implemented. Fulfillment requires provider status **finished**, full payment and matching invoice identity. Confirming/confirmed/sending never fulfill.
- New Telegram invoices use compact HTML captions, network-specific labels and copyable addresses, with no manual Check payment button. Provider polling edits the same caption only when its content changes, including received amount, completion and expiry. Old photo callbacks can register their message reference for compatibility. Delivery and wallet credits remain idempotent.
- Products are purchased with wallet balance only; stale direct-crypto purchase callbacks are rejected server-side. Existing direct-payment invoices still reconcile. NOWPayments wallet deposits default to floating rate and a $5 minimum (the admin may raise it). The actual deposit minimum is max(shop minimum, provider coin/network minimum). Live fixed/floating minimums are shown in payment settings. Floating invoices settle against the provider's current required amount, never an outdated lower quote.
- Order, customer and deposit views read persisted business records. Never seed paid orders, wallet balances or payment confirmations to make the dashboard appear live.
- Telegram's rules require Stars for digital goods sold inside bots. NOWPayments QR payments do not override Telegram/provider rules; the activation UI states this explicitly.

## Run & Operate
- Advertising uses a cookie-authenticated event stream at `/api/shop/advertising/events` to push current owner-scoped workspace snapshots after database changes. Reconnects rehydrate the list, counts and membership activity; the page no longer depends on five-second polling. Persistent account clients also process relevant Telegram group/self-membership updates (not ordinary messages), respecting account generation and existing connection containment.
- Advertising counts distinguish the current checkbox selection, eligible destinations for a new campaign (with exclusion reasons), and the server's running forwarding campaign. Checkbox changes never mutate an existing campaign. Background data/session transport failures retain the last verified screen and unsaved choices with a warning; confirmed sign-out, authorization rejection and identity changes still clear private query state. Unchanged session checks do not notify the UI.
- Large live-update snapshots must wait for the response stream to drain; a full send buffer is normal backpressure, not grounds to close the connection. The live-stream regression includes 211 groups and verifies subsequent changes arrive on the same connection.
- Removal from the dashboard and leaving Telegram are separate outcomes. Discovery's numeric target is a safe pinned chat identity even before its first successful permission check; public targets are pinned through read-only membership verification before posting checks. The worker repairs only automatic leave jobs affected by the known missing-identity pre-RPC failure, never uncertain leaves or conflicting identities. Unknown usernames must not be guessed, and successful/removed destinations must not be silently restored.
- Every failed account-group check disables that destination and stops its schedule. Destination-resolution failures are explicit group-scoped outcomes, distinct from transport failures or Telegram waits, and queue removal/leaving. Numeric IDs resolve directly before refreshing dialogs. Legacy cached-dialog resolution errors are rechecked under the verified account: successful rechecks remain disabled until explicitly enabled, while continued destination failures are removed. Error-state groups cannot be re-enabled until a successful check.
- Selection-based group bulk actions apply only to checked rows in the current status filter and search, never hidden selections. “Disable all shown” instead targets every enabled match, including unchecked groups, and ignores already-disabled groups; its confirmation freezes those exact identities and stopping follows the existing individual disable-switch/resume semantics. Removal requires a frozen, named confirmation, stops only those schedules, and preserves posting history and removed identities, including portable exports, to prevent rediscovery or replay. Disabling or removing from advertising is not leaving Telegram; do not enqueue leave jobs for these manual dashboard actions. Bulk endpoints are owner-scoped and atomic.


- Advertising discovery lists existing basic groups, supergroups and channels from up to 1,000 chats; it never joins or posts. Do not enable GramJS's broken `ignoreMigrated` option: filter left/deactivated/migrated basic chats locally. The UI reports added destinations, already-saved results or an empty scan. Membership/posting checks and explicit schedule starts remain separate.
- Personal-account advertising keeps one connected client through QR/phone login, two-step verification and promotion to discovery, group permission checks and scheduled posting. Its dedicated PostgreSQL advisory lease stays held between operations and through promotion; API calls also retain their owner lock. Keep only one installation using an authorization: independent database copies cannot share these locks. Clients are fully destroyed on cancellation, disconnect, replacement, failure, lease loss and shutdown. A failed disposal retains the lease rather than permitting a replacement client. Saved session/DC changes remain encrypted.
- GramJS 2.26's sender reconnect path ignores its `autoReconnect` flag. The driver explicitly guards sender creation, `reconnect`, queued `_reconnect`, RPC dispatch and DC changes; never remove these guards based on the flag alone. QR and phone authentication have bounded redirect retries; advertising sends keep their no-retry policy. Group entities are refreshed before reusing cached posting permissions. A lost pending login is not restored after a restart: cancel/review Devices before a fresh login.
- Revocation, restriction, identity mismatch, lease/disposal failures and missing posting evidence remain hard stops. Known transport closures/timeouts instead queue bounded network recovery: up to three attempts with 5/15/45-second backoff and a rolling ten-minute budget. Attempts are consumed before network IO and pending counts survive restarts. Recovery fully destroys the old client, reacquires its exclusive lease, pins the existing auth key/DC, and verifies the same account with a read-only call—never QR/code initiation or SDK request replay. A failed key/identity check stops immediately. Success leaves stopped groups stopped and moves overdue enabled groups to their next interval, not an immediate catch-up post. Uncertain sends still stop their affected group and are never replayed. An older transport-only stop can be explicitly queued through Retry saved connection; ordinary discovery cannot reopen it. Three failures or a rapid repeated-drop budget exhaustion require review rather than another automatic loop.
- The dashboard shows Reconnecting and hides new-login controls while recovery is pending. Paused schedules are never enabled by login or recovery. Structured diagnostics contain allowlisted operation names/error codes, never raw RPC payloads, exception text/stacks, codes, passwords, phones, app credentials or serialized sessions. Browser QR polling stops on errors. Do not test a merchant's live account or channel posting to diagnose a security notice; use RPC/browser mocks. Telecart cannot determine the cause of, or lift, Telegram's account restrictions or bot-token resets.
- Advertising “sent” requires a correlated Telegram message ID plus a read-back of that exact message in the selected group. Text, photo and GIF paths share this rule. A missing/ambiguous acknowledgement, wrong peer, missing/deleted message or failed read-back is uncertain and stops without retrying the send. Verified runs record their message ID in the activity note; it proves readability only at that time, not future visibility. Historical sent rows lacking that evidence remain intact but the dashboard labels them unverified. A successful verified post keeps its schedule running for the next configured interval; a connection failure stops it.

## Security & Operations

- Inventory accepts one `login:password` line per account, at most 500 per request. Records are encrypted with AES-256-GCM, owner/product AAD and a random nonce.
- Telegram bot tokens and NOWPayments API/IPN credentials entered in the admin dashboard are encrypted at rest using AES-GCM, per-owner associated data and a key derived from `SESSION_SECRET`. Ordinary APIs never return them. Explicit authenticated SQLite exports include portable readable values after a confidentiality acknowledgement. Preserve `SESSION_SECRET` for the live database; rotating it makes existing encrypted credentials unreadable.
- Encryption and deduplication keys derive from `SESSION_SECRET`. Preserve that secret: rotation without a data re-encryption migration makes existing inventory unreadable. Before production-scale use, design a dedicated versioned inventory-key rotation workflow.
- Never log credentials, return plaintext inventory to list APIs, store service API keys in ordinary settings, or include credentials in activity events.
- Product deletion cascades inventory. The frontend must explain and confirm this before deleting.
- Prices persist as integer USD cents. No administrator mutation may fabricate a paid invoice or confirmed wallet credit.
- Payment handlers use verified signatures, idempotent state transitions and atomic wallet/stock updates. A stock line is reserved at invoice creation. Local quote expiry does NOT release stock: only a verified provider terminal status can release it.
- Uncertain provider creation (timeouts) holds stock for manual investigation by merchant order ID. Never blindly recreate an invoice or assume a timed-out request did not reach NOWPayments. Partial/wrong-asset/child/repeated deposits require manual review.
- Exactly-once allocation/credit is enforced in PostgreSQL. Telegram cannot guarantee exactly-once message delivery: after an ambiguous send, retries may resend the same assigned line, never consume another. Buyer/admin status checks and repeated IPNs retry pending delivery.
- Existing paid/reserved inventory cannot be deleted through product cascades; archive those products. Do not auto-refund, reverse a wallet ledger entry or release reserved stock merely because the local clock expired.
